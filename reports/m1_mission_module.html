The Terrain Pipeline

00

What this module is responsible for

m1_mission is the first stage of the framework. Everything downstream — sizing, the architecture search, the dymos trajectory — assumes a flyable corridor already exists. This module produces it.

It takes two coordinates from a mission YAML and turns them into four things: a terrain model of the corridor between them, a flight path that clears that terrain, a feasibility verdict on that path, and a wind field that corrects airspeed to groundspeed. Nothing in it optimizes anything; it defines the world the optimizer later works in.

Three things changed in this pass

The fabricated-terrain source is gone; every DEM is now measured data traceable to a named dataset. DEM resolution defaults to the dataset's own posting rather than an arbitrary square grid. And the case study moved to a corridor that actually exercises the physics — 13.6 km across a ridge, with a 610 m net descent.

01

The case study

Hospital Enrique Garcés → Hospital de los Valles.

The previous corridor (Garcés → Metropolitano) was a 7.9 km hop inside the Quito basin. The new one leaves the basin entirely: it climbs to a 3,026 m ridge at the 7.9 km mark, then drops into the Cumbayá valley at 2,296 m. That combination — a terrain barrier that must be overflown followed by a sustained descent — is what makes it a real test of a hybrid VTOL rather than a cruise-dominated one.

Hospital de los Valles reads 2,295.9 m in NASADEM and 2,292 m in SRTMGL1 — squarely the Cumbayá valley floor, ~610 m below Garcés. Two independent datasets agreeing on a physically sensible elevation is what confirms the coordinates, rather than trusting a single geocoder.

The elevations in the YAML are those NASADEM measurements. They act only as a fallback: with a DEM loaded, _dem_anchored_ground_elev() takes pad altitudes from the DEM itself, so clearance checks and pad heights always come from one consistent terrain model.

The fabricated source was removed, not deprecated

source="synthetic" generated hand-authored terrain calibrated to two points and invented everywhere else. Asking for it now raises ValueError rather than silently falling back — a test pins that, because the provenance of a mission's terrain has to stay unambiguous.

Tests still need deterministic offline terrain, so the fabrication moved to tests/conftest.py, where it is clearly a fixture and cannot be imported from hpraptor. The fixture deliberately mirrors the real corridor's shape — valley, ridge, lower valley — so path tests exercise a genuine barrier.

04

Resolution

Why the default is now the dataset's own posting, and non-square.

Two changes. First, the grid is no longer forced square. A corridor between two facilities almost never is — this one is 3.24 : 1 — and an N×N grid oversamples one axis while starving the other. Starving longitude is the damaging case here, because that is the direction of flight: it is precisely the along-track terrain detail that clearance checking depends on.

Second, the default resolution is native: sampling at the dataset's own posting. Interpolating a 30 m dataset onto a 10 m grid invents no information, so native is the point of diminishing returns rather than an arbitrary number. For this corridor that is 195 × 631 = 123,045 cells at ~31 m spacing.

Build time is flat — it is one API call plus local resampling, so resolution genuinely is free. Query and path-building time are unchanged; RegularGridInterpolator is logarithmic in grid size and dominated by constant factors at these scales. The only real cost is 2.7 MB of disk.

And it buys 24 m of ridge

The last column is the point. A 60 × 60 grid smooths the ridge on the route down to 3,002 m; native resolves it at 3,026 m. That 24 m comes straight out of the 100 m cruise clearance margin — an unnecessary error, given it costs nothing to avoid.

Native is capped for safety: 2 M cells for the raster path (a memory bound), and 10,000 for the OpenTopoData path, where resolution is not free — 10,000 points is 100 calls, 10% of that server's daily quota. Beyond the cap both axes shrink by the same factor, so ground cells stay square.

05

The NASADEM path, end to end

One request, one response, parsed and resampled locally.

Why NASADEM, and why through OpenTopography

NASADEM is NASA's reprocessing of SRTM, merged with ICESat/GLAS altimetry and ASTER stereo imagery, using a newer phase-unwrapping technique. It is served here through OpenTopography, not NASA's own LP DAAC: LP DAAC distributes 1°×1° .hgt tiles over authenticated HTTPS with no point-query API, which would have meant an Earthdata Login, tile-coverage maths and multi-tile mosaicking. OpenTopography returns the corridor already clipped and mosaicked, from a standalone account unrelated to NASA's.

The request

the only network call this path makes
GET https://portal.opentopography.org/API/globaldem
      ?demtype=NASADEM
      &south=-0.253400  &north=-0.199400
      &west=-78.570300  &east=-78.395300
      &outputFormat=AAIGrid
      &API_Key=<OPENTOPOGRAPHY_API_KEY>
Why AAIGrid and not GeoTIFF

GeoTIFF would have required rasterio, and with it a GDAL binary dependency. AAIGrid — ESRI ASCII Grid — is plain text that numpy parses directly, so this module adds no new package dependencies at all. The cost is a bulkier response, which is why a size guard exists. For mission-scale corridors the trade is overwhelmingly favourable: this corridor arrives in 0.6 MB.

The response

Verified against the live API rather than assumed — the real header for this corridor:

actual AAIGrid header
ncols        630
nrows        194
xllcorner    -78.570416666651
yllcorner    -0.253472222231
cellsize     0.000277777778     ← 1 arc-second = 30.9 m
NODATA_value -32768

122,220 samples, zero nodata cells. The parser handles both the xllcorner/yllcorner (cell corner) and xllcenter/yllcenter (cell center) header variants, both cellsize and separate dx/dy, and is case-insensitive — the live server uses the corner form, but tolerance is cheap and a mis-parse would be silent.

Two details that would corrupt terrain silently

Row order

AAIGrid stores the northernmost row first. Every other array in m1_mission is ascending-latitude. The parser flips with np.flipud. Getting this wrong mirrors the terrain north–south — which still looks like plausible mountains, so no assertion downstream would catch it.

Cell centers vs corners

xllcorner names the corner of the lower-left cell, but samples sit at cell centers — half a cell in. Ignoring the offset shifts the whole grid by ~15 m. At 30 m posting on a 45° slope that is a ~15 m elevation error, right where clearance matters most.

06

The data contract

Why swapping the source changed nothing downstream.

Vertical datum

OpenTopography serves NASADEM as WGS84 horizontal (EPSG:4326) with EGM96 geoid vertical (EPSG:5773): orthometric metres above mean sea level. That is the identical convention SRTM already used here. Had NASADEM been served on the WGS84 ellipsoid instead, every elevation would be offset by the geoid separation — roughly +26 m at Quito — a smooth, entirely plausible-looking bias that no test would flag.

Consequence

DEMInterface, TerrainAnalyzer and WindModel required zero changes. They cannot distinguish a NASADEM DEM from an SRTM one except by reading the source string, and they never do.

Cache invalidation

A cached file is reused only when bounds, source label and both grid dimensions match. The source label carries the dataset name, so switching demtype from NASADEM to COP30 — same bounds, same resolution — correctly rebuilds instead of silently serving the wrong dataset.

07

Guards and failure modes

Every check runs before a quota-limited call is spent.

fetch_raster() validates cheapest and most local first, so a mistake never costs a request: bounding-box sanity → dataset coverage (NASADEM spans 60°N–56°S; the error suggests COP30, and a test verifies that really is global) → request size → credentials, resolved last, with setup instructions in the error itself.

Errors that name the real cause

The OpenTopoData path used to report every failure as "Check network connectivity". A quota exhaustion — the most likely failure on a 1,000/day shared cap — sent you debugging entirely the wrong thing.

The module, file by file

3,019 lines across seven files, plus a 179-line test fixture module.

opentopography.py 525 lines · new

OpenTopography Global DEM client. Credential resolution, the four pre-flight guards, HTTP with typed error mapping, the AAIGrid parser, and bilinear resampling onto the pipeline grid. Knows nothing about missions — it takes a bbox and returns elevations.

dem_visualizer.py 483 lines · new

Two figures — a four-panel overview and a two-DEM comparison — plus a CLI. Deliberately here rather than in postprocessing, which imports the whole propulsion stack at load time; a DEM should be inspectable before any vehicle exists.

srtm_downloader.py 677 lines · rewritten

The ingestion orchestrator despite the legacy name: build_dem(), the auto resolver, native_grid_shape(), the OpenTopoData point-query path, slope/hillshade, and the CLI. The synthetic generator is gone.

builder.py 677 lines · fixed

PathBuilder and three strategies — HIGH_OVERFLY, TERRAIN_FOLLOW, MINIMAL_ENERGY — plus the new _fit_angles_to_route() (see §09) and FacilityNode.

dem.py 297 lines · unchanged

DEMInterface — the read side. Bilinear point and batch elevation queries, terrain profiles along a line, and geodesy helpers (haversine, bearing, destination point). Source-agnostic by construction.

terrain.py 263 lines · unchanged

TerrainAnalyzer turns a path plus a DEM into a TerrainReport: AGL profile, clearance violations, minimum-AGL location, and a smooth squared-deficit penalty suitable for an optimizer.

wind_model.py 97 lines · unchanged

Logarithmic boundary-layer wind shear V(h) = V_ref · ln(h/z₀) / ln(h_ref/z₀), headwind projection onto the path heading, and the airspeed→groundspeed correction.

tests/conftest.py 179 lines · new

Where fabricated terrain now lives: a fixture builder writing valid .npz files directly, a DEM-anchored node fixture, and a stub that redirects the OpenTopography client so ingestion can be tested with no key, no network and no quota spent.

09

What the harder corridor exposed

Three defects the 7.9 km route had been hiding. Two fixed; one is a limitation to know about.

1 · Paths overshot the destination fixed

MINIMAL_ENERGY uses deliberately shallow 5°/4° angles. On this route that needs 6.7 km to climb and 12.2 km to descend — 19.2 km of a 13.6 km route. The builder budgeted cruise as max(total − departure − arrival, floor), so cruise clamped to its 200 m floor and the path simply overran: a ground track 42% longer than the route, with the aircraft "landing" 5.7 km past the destination — while every distance-derived energy number was computed for that impossible flight.

_fit_angles_to_route() now steepens both angles instead, scaling their tangents by exactly the factor needed and capping each at the airframe limit. Ground tracks are back to 1.00× direct. HIGH_OVERFLY carried the same latent bug — its steeper angles simply hadn't triggered it yet — and uses the same fix.

high_overfly1.001 ×1.001 ×

2 · Strategy selection could choose a path through the ridge fixed

When no strategy fully cleared terrain, the selector fell back to ranking on energy alone. On this corridor that picked minimal_energy at min AGL −165.6 m — straight through the ridge — over high_overfly, whose single "violation" was −0.4 m of pad-level interpolation noise, because the deep-violating path saved 159 Wh.

run_mission.py — the fallback ranking
# Ranking on energy here is actively unsafe. Depth of violation
# dominates; energy only breaks ties between equally-unsafe options.
best_key = min(
    candidates,
    key=lambda k: (-candidates[k].terrain_report.min_agl,
                   candidates[k].total_energy_wh),
)

The run now selects high_overfly and says plainly why: “Selecting 'high_overfly' as the LEAST unsafe (min AGL −0.4 m, 1 violation) — not the cheapest. Do not fly this without resolving clearance.”

3 · Analytical sizing does not meet the SOC reserve here known limitation

On this corridor all three hybrid architectures finish at SOC 0.000, against a declared 0.15 reserve. The mechanism: HybridEnergyManager's power split draws the mission almost entirely from the battery — series burns 0.017 kg of a 1.12 kg fuel tank and takes the rest electrically. Only all_electric, whose battery is sized for the whole mission, finishes with margin (0.284).

Not caused by this work, and not hidden

compute_initial_sizing() is analytical — it sizes from payload fractions and a constraint diagram, and never simulates the mission, so it never enforced min_battery_soc. The old 7.9 km route simply stayed inside the envelope. This is precisely the gap the m8 MDAO optimizer exists to close; it already carries g2_energy_margin as an explicit constraint.

Rather than weaken the assertion, the suite now pins the current behaviour in test_analytical_sizing_does_not_guarantee_the_soc_reserve, which fails loudly if a future change makes the reserve hold — so the finding cannot quietly disappear.

Running it

One-time setup

PowerShell · persists for new terminals
setx OPENTOPOGRAPHY_API_KEY "your-key-here"

# current session only:
$env:OPENTOPOGRAPHY_API_KEY = "your-key-here"

The key is read from the environment only — never written to a repo file — and .gitignore now covers a bare .env file as well as the .env/ directory it already had.

Everyday use

nothing to pass — auto picks NASADEM at native resolution
python run_mission.py configs/quito_mission.yaml

# force a source, a dataset, or a square grid
python run_mission.py configs/quito_mission.yaml --dem-source nasadem
python run_mission.py configs/quito_mission.yaml --dem-demtype COP30
python run_mission.py configs/quito_mission.yaml --dem-resolution 300

# build a DEM on its own and inspect it — still one API call
python -m hpraptor.m1_mission.srtm_downloader \
    --mission configs/quito_mission.yaml \
    --output data/dem/quito_cumbaya_corridor.npz --plot

# compare two datasets over the same corridor
python -m hpraptor.m1_mission.dem_visualizer data/dem/quito_cumbaya_corridor.npz \
    --compare data/dem/other.npz --output results/dem_diff.png

Still open

  1. The SOC shortfall is the next module's problem. Analytical sizing puts the hybrids at SOC 0 on this corridor. That is the m8 optimizer's job, and it already has the constraint — but until it runs, no hybrid result on this route is flight-valid.
  2. Terrain clearance is not yet satisfied. The best strategy grazes the pad by −0.4 m and the others penetrate the ridge. The selector now surfaces this loudly instead of hiding it, but the path geometry itself still needs work for this corridor.
  3. Nothing is committed. All of this sits in the working tree on feature/hybrid-mdao-optimizer.
  4. The key is in our chat transcript. It is a free-tier key, but regenerating it in MyOpenTopo is the cautious move; the live test re-verifies a new one in about twelve seconds.
  5. srtm_downloader.py is now a misnomer. It orchestrates two sources, only one of which is SRTM. Renaming it to dem_sources.py would be honest but touches every import site — worth doing deliberately, not incidentally.
