What this framework does

In one sentence: it designs a hybrid VTOL delivery drone by letting a computer search for the best numbers, instead of a person guessing them.

Before this work, hpraptor was a set of physics calculators — one for the wing, one for the structure, one for drag, one for the propulsion system. A person would pick numbers (wing size, which of six propulsion architectures to use, how fast to fly) and the calculators would tell you whether that design works and how much energy it burns. Getting a good design meant guessing, running the calculators, and guessing again.

OpenMDAO wraps those same calculators so a search algorithm can do the guessing instead — and instead of guessing blindly, it uses the mathematical slope of "if I nudge this number, does the result get better or worse" to move directly toward improvement. That's the whole idea: same physics, but now searched intelligently rather than by hand.

Three studies exist, each searching a bigger question:

sizing
pick the vehicle's shape, structure, and propulsion mix for one representative flight condition. Seconds to solve.
cruise
pick a full speed/power schedule for the level-flight segment alone, changing over time rather than one fixed number. Tens of seconds.
mission
the real thing: pick a schedule for the entire flight — takeoff, transition, cruise, transition, landing — all five phases together. Tens of seconds to a few minutes.

The optimization problem, fully described

Every study the framework runs follows exactly this shape.

minimize   f(x)
by varying xi,lower ≤ xi ≤ xi,upper    i = 1 .. nx
subject to gj(x) ≤ 0         j = 1 .. ng
            hl(x) = 0           l = 1 .. nh

Four pieces, translated:

x
design variables — the numbers the optimizer is allowed to change. Wing area, spar thickness, how fast to fly at each moment, which propulsion architecture to lean toward.
f(x)
the objective — the one number to make as small as possible. Here: total energy the mission burns.
g(x) ≤ 0
inequality constraints — things that must stay within a safe range: the wing must not overstress, the wing must not stall, the battery/fuel must be enough to actually finish the mission.
h(x) = 0
equality constraints — things that must match exactly: the laws of physics must hold at every instant in the flight, and one flight phase must hand off smoothly to the next.

This is not a metaphor — it's read directly out of the running model, not written down separately, so it can't drift from the code. Two concrete examples follow.

Example 2 — the full mission: how five lines become 361 numbers

This is the part worth seeing in detail, because it's not obvious from the summary count. Nobody wrote 361 variables by hand. Each phase is declared once — five states, four controls — and dymos multiplies that by however many points in time ("nodes") the phase is broken into. More segments = a more accurate trajectory = more numbers for the optimizer to choose. The code, for one phase (cruise):

hpraptor_mdao/trajectory/mission_problem.py

ph = dm.Phase( ode_class=MissionPhaseODE, transcription=dm.GaussLobatto(num_segments=8, order=3), # -> 9 state nodes, 17 control nodes ) ph.add_state("x", rate_source="x_dot", units="m") # -> traj.cruise.states:x (9) ph.add_state("h", rate_source="h_dot", units="m") # -> traj.cruise.states:h (9) ph.add_state("v", rate_source="v_dot", lower=18.0, upper=50.0) # -> traj.cruise.states:v (9) ph.add_state("m", rate_source="m_dot", lower=1.0) # -> traj.cruise.states:m (9) ph.add_state("SOC", rate_source="SOC_dot", lower=0.15, upper=1.0) # -> traj.cruise.states:SOC (9) ph.add_control("T_vtol", lower=0.0, upper=294.3) # -> traj.cruise.controls:T_vtol (17) ph.add_control("T_cruise", lower=0.0, upper=235.4) # -> traj.cruise.controls:T_cruise (17) ph.add_control("k_electric", lower=0.0, upper=1.0) # -> traj.cruise.controls:k_electric (17) ph.add_control("alpha_deg", lower=-5.0, upper=12.0) # -> traj.cruise.controls:alpha_deg (17)

That's the actual mechanism behind "the physics must hold at every instant": each state (x, h, v, m, SOC) gets one defect equation per phase per interior node, saying the change dymos computed between two points must match what the ODE (MissionPhaseODE, i.e. m6_dynamics plus the blended propulsion physics) says it should be. A person never writes these — they exist because a state and a transcription were declared, and dymos derives the rest.

How the pieces are wired together

Two different kinds of "wiring": modules feeding each other for one instant, and phases handing off across time.

Sizing: a loop that closes on itself

Vehicle weight affects how big the wing needs to be. Wing size affects drag. Drag affects how much power is needed. Power needs affect battery/fuel weight. And battery/fuel weight feeds back into vehicle weight — the loop closes on itself. The framework resolves this by iterating it automatically until every number agrees with every other:

m2wing / fuselage / rotor / tail geometry
→
m3 + m4structure weight + aerodynamic drag
→
m5power needed, battery/fuel weight
→
mass closureadds it all up to a new vehicle weight
↻ fed straight back into m2, repeated until every number stops changing

This self-consistency check runs automatically every single time the optimizer wants to evaluate one candidate design — before it even looks at whether that design is good.

The mission: five phases, linked end to end

VTOL climb→ transition fwd→ cruise→ transition back→ VTOL land

Each phase is its own mini flight-schedule problem. They're stitched together by requiring that altitude, mass, and battery charge match exactly where one phase ends and the next begins — the flight is continuous, not five disconnected pieces. Airspeed is deliberately not forced to match at the VTOL boundaries, because it means something different there (climb rate hovering, versus forward airspeed once flying like a plane) — forcing those to match caused one of the problems described below.

Choosing the propulsion architecture

The framework's most distinctive piece — searching across six discrete choices with the same gradient-following method used for continuous numbers.

There are six propulsion architectures to choose from: all-electric, series hybrid, parallel hybrid, series-parallel, turbo-electric, fuel cell. Normally, comparing them means running the whole optimization six separate times. Instead:

  1. Six numbers (z_arch) are turned into six blend weights that always add up to 100% — e.g. 85% series hybrid, 10% all-electric, 5% spread across the rest.
  2. Every physical quantity that depends on architecture (propulsion weight, fuel burn, battery draw) is computed as that same weighted blend.
  3. The optimizer nudges the six numbers exactly like any other design variable, using the same gradient-following method.
  4. A penalty added to the objective pushes the blend back toward a single real choice — it is zero only when one architecture reaches 100% and the rest are at 0%, and grows the more "mixed" the blend is.

One pass of the optimizer effectively searches all six architectures — and picks a trajectory and a vehicle shape that suit the winner — at the same time.

One real quirk of this trick

Starting from "evenly blended" (all six at 1/6 each) is a mathematical tie: by symmetry, the penalty has exactly zero slope there, so the optimizer gets no hint which way to move. The fix is to start six separate solves, each nudged toward a different architecture, and keep whichever the optimizer likes best — not a bug, just something this specific trick requires.

How the "slope" is actually computed

The one piece of machinery under all of this, in one paragraph.

To know which direction to nudge 361 different numbers, the optimizer needs to know how sensitive the objective is to each one. Deriving 361 slope formulas by hand is impractical and error-prone. Instead, every small calculation in the code (drag, thrust, fuel flow, and so on) is evaluated using a numerical trick called complex-step differentiation: nudge the input by an infinitesimally small imaginary number, and the sensitivity falls straight out of the result to machine precision — no hand-derived formula, no approximation error.

The catch: this trick breaks on any calculation that branches on a comparison — an if, a max(), an overflowing tanh. A large part of the work this session was rewriting exactly those spots as smooth, always-differentiable approximations instead — full detail is in the companion migration report.

What's still open

Asked directly: yes, there are real gaps left. Here they are, ranked by how much they matter.

1 — sizing and the mission are not yet talking to each other

The mission study takes wing area, aspect ratio, drag, and rotor size as fixed numbers typed into the trajectory problem — they don't yet come from the sizing optimizer's own answer. Today you get two separate "best" answers that are not guaranteed to agree with each other. This is the single largest remaining integration gap.

2 — architecture choice across the full mission is still being validated

The six-way warm-start search (see the quirk above) is running now. all_electric has converged (objective 0.2029, 643 iterations); the other five are in progress. Each warm start is its own 361–367-variable solve, so this genuinely takes a while — it is not stuck, it is just a long-running job.

2b — a long-running solve doesn't survive a CLI session restart

The first attempt at this search was silently killed partway through when the terminal session restarted — the background process had no independent way to keep running once its parent shell was torn down. It left one confirmed result (the all_electric figure above) and no error, which could easily be mistaken for the job simply finishing early. Worth knowing if a long solve looks like it "disappeared."

3 — a data inconsistency in the fuel-cell model

The fuel cell's declared maximum power (8000 W) doesn't match what its own physical curve can actually deliver (2373 W) — and its weight is calculated from the declared, wrong number.

4 — the more detailed aerodynamics tool isn't in the loop

A more accurate aerodynamics library (AeroSandbox/VLM) is available but can't currently be used inside the optimizer — it isn't compatible with the complex-step slope trick above. The simpler, faster aerodynamics formula is used instead. Getting VLM-level accuracy into the loop needs an extra step (fit a smooth stand-in from VLM results) that hasn't been built yet.

5 — two trajectory codepaths still exist side by side

The older trajectory optimizer (built directly on CasADi, not OpenMDAO) is intentionally still in the repository as an independent cross-check. It gets removed once the new five-phase mission is fully validated — not before, since it's currently the only thing to check the new one against.
